# AI 导师讲得很顺，用户真的学会了吗？

**AI PM 每日精选 · 2026-11-15 初稿 · 2026-11-16 发布复核 · 学习产品 × Harness × 结果评估**

今天选 [LearnHarness](https://github.com/amosblomqvist/learnharness)，讨论一个容易被演示效果掩盖的问题：**当 AI 能诊断、讲解、出题、记忆，产品经理应该用什么证据证明用户获得了可迁移的能力？**

这是一份独立原创中文产品分析，不是官方教程、源码镜像或实际测评。未安装或运行 LearnHarness，未调用模型，也没有采集真实学习者数据。以下实验、评分、指标与验收案例均为自拟设计，结果全部为“待测”。

## 一分钟结论

- 先明确用户要完成的真实任务，再决定要不要做 AI 导师。
- 把“看过”“答对”“延迟后能独立应用”分开记录。
- Harness 的产品价值在于维护任务状态、控制下一步和处理失败；更多对话并不自动带来更好的学习。
- 学习图谱应展示证据来源、适用条件与修正记录，不能把节点数量包装成能力评分。
- 对照实验要比较相同时间与内容条件下的学习结果，同时计算人工纠错和系统运行成本。

## 2. 从实现读出三个产品问题

上游将学习过程组织为诊断起点、规划路径、教学和练习，并用持续保存的知识图谱串联会话。其 [入门文档](https://github.com/amosblomqvist/learnharness/blob/cb25c8e49b85eed9e78315584731cad73a0118a6/docs/getting-started.md)特别说明：图谱保存命题、推理关系和来源，不是掌握程度评分；用户自报信心也不是独立测量。

### A. 系统记录了什么，用户就会以为什么？

假设一个“理解了召回率”的节点出现在图谱里，用户可能以为系统已确认自己掌握了这个概念。但节点也可能只是由讲解或资料提取得到。

**本文建议：**在产品数据模型中区分“已呈现的知识”和“能力证据”。能力证据至少保留题目、作答时间、提示次数、评分依据与适用范围。没有独立应用证据时，状态应保持未知，而不是自动升级为“已掌握”。

### B. 用户中途改变主意，系统还能尊重最新意图吗？

[v0.6.1 发布记录](https://github.com/amosblomqvist/learnharness/releases/tag/v0.6.1)包含一项有产品意义的修复：避免上下文压缩覆盖新保存的跳过、问题关闭、方向调整和暂停状态。

**本文建议：**把“用户刚刚暂停了”当成必须保存的任务状态，而不是可以由模型总结自由改写的一段聊天。验收时要专门测试暂停、重试、断线和中途改目标，不能只测一口气完成课程的路径。

### C. 图谱中的推理会不会越合并越武断？

[v0.6.0 的已知限制](https://github.com/amosblomqvist/learnharness/releases/tag/v0.6.0)披露，等价命题合并可能丢失必要前提。v0.6.1 发布说明没有声明修复该项；本文未复现，也未证明当前所有场景仍然受影响。

**本文建议：**把它转成回归用例：原命题“在标注质量合格、测试集分布相近时，某项指标改善才支持上线判断”，不能合并成“指标改善就应该上线”。缺条件的知识，会把学习产品变成错误决策的放大器。

## 3. 先定义任务，再决定要多复杂的系统

设想一个虚构产品：帮助成年初级 AI 产品经理，学会评审客服检索增强生成（RAG）方案。任务终点不是“学完 RAG”，而是：

> 面对一份陌生的评测报告，能指出证据缺口，选择合适的下一项实验，并解释为何暂不上线或小范围试点。

| 用户需要 | 最小可比方案 | 增加自适应系统的理由 |
| --- | --- | --- |
| 临时查一个术语 | 搜索、短文或普通问答 | 通常先验证是否真有跨会话需求 |
| 结构化入门 | 固定教材、案例和练习 | 若起点差异很大，再验证诊断是否减少无效内容 |
| 跨场景应用 | 多样案例、独立评分与反馈 | 验证系统是否识别误解，而不是重复同一种题 |
| 长期学习 | 复习计划、记录与可修改目标 | 验证持久状态能否减少重复诊断和错误延续 |
| 工作中高风险决策 | 专业流程、人工复核与权限控制 | 学习结果不能直接授权系统替用户做真实决策 |

**进入开发的前提：**已经找到一个现有流程无法低成本解决的具体失败，例如“用户能复述定义，但面对新报告仍把准确率当成唯一上线依据”。如果只有“想加一个 AI 导师”，问题定义还不够。

## 4. 把 Harness 写成可以验收的产品状态

以下是本文设计的状态与守门条件，不是在描述 LearnHarness 已具备的全部能力。

| 状态 | 要留下的证据 | 允许进入下一步的条件 |
| --- | --- | --- |
| 目标待确认 | 用户要完成的任务、时间约束、退出条件 | 用户认可目标；任务适合当前产品 |
| 起点待诊断 | 少量诊断题及错误解释 | 能定位下一项需要验证的知识缺口 |
| 方案待选择 | 教学计划、可跳过内容和预计投入 | 用户可以修改计划，不必接受全部路径 |
| 学习进行中 | 作答、反馈、提示和修正 | 新一轮活动确实响应了最新证据 |
| 效果待验证 | 陌生案例的独立作答 | 按预先确定的口径评分，不能由系统自我宣布成功 |
| 延迟复测 | 延迟后的无提示表现 | 能识别遗忘、迁移失败及需要复习的内容 |
| 暂停或终止 | 最后有效状态、已计成本、恢复入口 | 不在用户暂停后继续生成新任务或扩展范围 |

产品经理要追问：哪个状态是权威记录？网络响应成功是否只意味着“请求已接收”？失败后会重复出题、重复计费或覆盖刚提交的答案吗？

上游 [架构文档](https://github.com/amosblomqvist/learnharness/blob/cb25c8e49b85eed9e78315584731cad73a0118a6/docs/architecture.md)区分持久记录、运行状态和界面投影。这为上述问题提供了实现阅读入口，但不是本文对可靠性的测试结论。

## 5. 一份能开展的对照实验

### 假设

在相同学习时间和内容范围内，自适应诊断与练习能改善陌生业务案例的决策质量，并且新增成本可接受。

### 方案

1. 先让少量成年目标用户做可用性试点，发现流程问题；这一步不宣称统计显著。
2. 正式实验前按前测水平分层随机分组。依据最小有业务价值的差异、试点方差和流失估计确定样本量，不随意选一个人数宣布有效。
3. A 组使用高质量固定教材、案例、练习及常规反馈。B 组使用相同内容范围和时间预算的自适应流程。
4. 两组采用相同的评价标准。保留训练之外的新案例，避免把练过的答案当成迁移能力。
5. 立即测试、48 小时后测试和 7 天后测试使用难度相近但不重复的题。这些时间点是示例，可按真实使用周期调整。
6. 隐去组别，交给独立评审者评分；部分样本双人复核，记录分歧和仲裁。模型可以辅助整理，不单独决定效果。
7. 记录退出与失访，按预定分析口径报告全部入组用户；同时公开完成者结果和不同缺失假设下的敏感性分析，避免只展示留下的人。
8. 试验开始前锁定主要指标、停止条件、分析方式和验收门槛，避免看完结果再挑赢的指标。

### 指标卡

| 指标 | 建议口径 | 防止误读 |
| --- | --- | --- |
| 主要结果 | 延迟测试中新案例的独立评分 | 使用固定量表，区分答案与推理依据 |
| 迁移成功率 | 无提示达到合格线的新案例数 ÷ 有效新案例数 | 不能用练习原题替代；保留学习者层面的差异 |
| 提示依赖 | 每次正确任务使用的提示数及提示深度 | 提示后答对不记为独立完成 |
| 严重误导率 | 导致关键结论错误的反馈数 ÷ 被审计反馈数 | 报告抽样方法；零观察错误不等于零风险 |
| 修正负担 | 用户和审核者纠正内容、状态所花时间 | 计入重复作答、错误图谱清理和恢复 |
| 单位有效学习成本 | 相关运行、人工复核及维护成本 ÷ 达标学习者数 | 达标人数为零时不可报告一个正常的低单价 |
| 退出与失访 | 按组报告人数、原因和测试完成比例 | 留存好可能是兴趣高，不足以证明学得好 |

评分量表可设置四项：识别证据缺口、选择下一项实验、解释权衡、说明上线边界。每项 0–2 分：缺失或关键错误为 0；方向正确但证据不足为 1；依据完整且适用范围清楚为 2。**这是自拟教学量表，不是行业标准，需先校准评审一致性。**

## 6. 八个纸面验收案例

以下案例全部为合成设计，当前结果均为 **待测**。

| 编号 | 输入或故障 | 应观察到的产品行为 | 不合格信号 |
| --- | --- | --- | --- |
| T01 | 用户猜对选择题，但解释完全错误 | 继续诊断具体误解；不只依据选项判定掌握 | 直接跳过必要内容 |
| T02 | 用户说“我很懂”，陌生案例却无法说明依据 | 区分自报信心和能力证据 | 用信心覆盖作答证据 |
| T03 | 上一题给过答案，本题只是换了名词 | 标记近似题，另用未见案例测迁移 | 把记住答案当成学会 |
| T04 | 用户暂停后，后台恰好进行上下文压缩 | 最新暂停状态保留；不擅自继续新教学任务 | 恢复为旧计划并继续执行 |
| T05 | 提交答案时断网，用户点击重试 | 先核对已有提交，避免重复产生同一条有效记录 | 重复评分、扣次数或推进两步 |
| T06 | 合并两个命题，其中一个依赖额外前提 | 保留适用条件和来源；不扩大结论 | 有条件结论被改成无条件结论 |
| T07 | 用户纠正一条过时知识 | 后续检索能看到修正、来源及冲突，不只新增一个节点 | 旧结论继续高置信出现 |
| T08 | 成本字段缺失，或使用未定价模型 | 显示未知项及统计覆盖范围 | 将未知费用显示为零并宣称免费 |

T04 受到近期版本修复启发，T06 受到已知限制启发；其他案例是本文的产品设计。用例存在不代表上游已经通过，也不代表本文发现了这些故障。

## 7. 数据与成本：决定产品能否真实使用

学习对话可能包含个人弱点、工作资料或错误认知。试点应优先使用自拟或公开材料，并让参与者知道哪些内容会交给哪些服务处理。

上游 [入门文档](https://github.com/amosblomqvist/learnharness/blob/cb25c8e49b85eed9e78315584731cad73a0118a6/docs/getting-started.md)说明，本地保存与本地处理不同；模型、检索和语音服务仍可能接收内容。文件访问也不是只限用户选择的文件夹。产品评审需要明确数据流、访问范围、删除与纠错入口，不把“本地优先”直接写成隐私保证。

[成本文档](https://github.com/amosblomqvist/learnharness/blob/cb25c8e49b85eed9e78315584731cad73a0118a6/docs/compaction-accounting.md)区分已知 API 费用估算、订阅用量与未定价路径。PM 的账本还应包含：诊断、授课、练习、后台整理、重试、人工审核和维护。不能用一个会话的估算金额代表服务一位学习者的完整成本。

[v0.6.0 发布说明](https://github.com/amosblomqvist/learnharness/releases/tag/v0.6.0)还说明社区插件属于受信任本地代码，并非沙箱扩展。学习内容的质量评估不能代替软件执行与数据访问风险评估。

## 8. 30 分钟产品练习

- **5 分钟：**选择一个明确的成年用户群，写出“学会后要独立完成的任务”。

- **10 分钟：**设计三道陌生案例、评分量表与提示记录方式。
